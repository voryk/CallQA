# CallGuard AI — техническое задание и план разработки

**Заказчик кейса:** ПАО КБ «Центр-инвест»  
**Команда:** 5 человек  
**Срок хакатонного MVP:** 4 дня  
**Цель после хакатона:** подготовка к пилотному внедрению в банковской инфраструктуре (не означает автоматического допуска в промышленную эксплуатацию).

## 1. Продукт и бизнес-цель

CallGuard AI — локальная веб-платформа для автоматического приёма, расшифровки, анализа и контроля качества телефонных разговоров операторов. Руководитель получает объективные, проверяемые KPI, причины оценок, ссылки на фрагменты записи, динамику качества и экспорт отчётов. Оператор видит разрешённые ему звонки и рекомендации. Аудио и текст не передаются в облачные сервисы.

**Основной пользовательский сценарий:** авторизоваться → загрузить WAV/MP3/OGG → увидеть очередь → дождаться расшифровки → проверить диалог и таймкоды → получить оценку и доказательства нарушений → посмотреть дашборд → экспортировать CSV/JSON.

## 2. Принципы и границы

- Offline-first: обработка аудио, транскриптов и AI-оценок выполняется в локальной инфраструктуре; модели скачиваются заранее. Запрещены внешние AI API и скрытая отправка телеметрии с чувствительными данными.
- Доказуемость: у каждого замечания есть критерий, цитата/фрагмент и таймкод либо статус «недостаточно данных». Нельзя представлять вероятностные выводы как достоверные факты.
- Human-in-the-loop: руководитель может проверить и скорректировать AI-оценку, сохранив исходный результат и запись об изменении.
- Безопасность по умолчанию: минимум прав, ограничение доступа к файлам, секреты вне репозитория, аудит, срок хранения.
- Оценка качества не должна автоматически использоваться для кадровых санкций без проверки человеком.
- Для банка необходимы отдельные согласования по ИБ, персональным данным, интеграциям и нагрузочным испытаниям.

## 3. Функциональные требования

### 3.1 Пользователи и доступ
- Вход/выход, безопасное хранение паролей, смена пароля.
- Роли: администратор (настройки и пользователи), руководитель (звонки своей группы, аналитика, проверка оценок), оператор (только разрешённые собственные звонки).
- Серверная проверка прав на каждый запрос, включая скачивание аудио и отчётов.
- В перспективе: корпоративный SSO/LDAP/OIDC, MFA, группы и подразделения.

### 3.2 Звонки и очередь
- Загрузка одного или нескольких файлов WAV/MP3/OGG; ограничение размера и длительности; проверка фактического типа файла, а не только расширения.
- Поля: идентификатор, оператор, дата/время, длительность, формат, статус, ошибки, метаданные, ссылка на защищённый локальный файл.
- Статусы: queued, processing, completed, failed; повторная обработка и просмотр ошибки.
- Очередь Redis + RQ, один AI-worker по умолчанию на ноутбуке; не запускать несколько тяжёлых моделей одновременно.
- Переживание перезапуска: состояние задач хранится в PostgreSQL; предусмотрена сверка «зависших» задач.
- Безопасная работа с временными файлами и очистка после обработки.

### 3.3 Распознавание и диалог
- FFmpeg нормализует входные форматы; faster-whisper работает локально, режим CPU int8 для Intel i5-1235U.
- Русский язык как основной; текст, сегменты, start/end, при возможности уверенность.
- Роли «оператор/клиент» назначаются только при наличии надёжного источника (двухканальная запись или проверенная диаризация). При неуверенности показывать «говорящий 1/2» или «не определён».
- Просмотр транскрипта синхронно с аудиоплеером; поиск по тексту.
- Коррекция расшифровки человеком с журналом изменений (после MVP).

### 3.4 Анализ качества
- Локальная LLM через Ollama (необязательный модуль MVP), плюс резервный rule-based движок.
- Настраиваемые критерии и веса: приветствие/представление, вежливость, выявление потребности, полнота ответа, соблюдение скрипта, корректное завершение, решение вопроса.
- Вывод: оценка 0–100, оценки критериев, найденные нарушения, текстовые основания с таймкодами, рекомендации, версия правил/модели.
- Тональность — оценочная метрика с пометкой о возможной ошибке; не приписывать эмоции человеку как установленный факт.
- Среднее время ответа вычислять только при корректных временных метках и определённых ролях; иначе null/«недоступно».
- Возможность повторно оценить запись при изменении правил; хранить историю оценок.

### 3.5 Аналитика и экспорт
- Дашборд: число звонков, средний балл, доля звонков с нарушениями, распределение по критериям, динамика по датам, список проблемных звонков.
- Фильтры: период, оператор, статус, диапазон оценки, критерий.
- Рейтинг операторов с числом проанализированных звонков (не делать выводы по единичной записи).
- Экспорт CSV/JSON: call_id, operator_id, started_at, duration_sec, score, violation_rate, response_time_sec (nullable), sentiment (nullable), status, criteria, violations.
- PDF-отчёт — после выполнения обязательного CSV/JSON.

### 3.6 Администрирование
- Настройка весов KPI и скриптов, просмотр очереди и ошибок.
- Политики хранения и удаления аудио, транскриптов, отчётов.
- Журнал действий: кто, когда, к какому ресурсу обращался и что изменил (без секретов и избыточных персональных данных в логах).

## 4. Нефункциональные требования

- Полностью локальное развёртывание; Windows для разработки, Linux-сервер для пилота.
- 10-минутный звонок: целевое время обработки не более 3–5 минут **на согласованном целевом оборудовании**; измерить отдельно на ноутбуке и не обещать результат без теста.
- Поддержка нескольких пользователей и очереди из множества файлов.
- Данные сохраняются после перезапуска; корректная обработка ошибок, таймаутов и повторов.
- API документирован через OpenAPI; автоматизированные тесты, миграции БД, инструкции запуска и восстановления.
- Для пилота: TLS, резервные копии и проверка восстановления, контроль зависимостей и образов, ограничения сетевого доступа, управление ключами, аудит, тесты безопасности и требования банка.

## 5. Технологический стек

- **Backend:** Python 3.12, FastAPI, Pydantic, SQLAlchemy 2, Alembic, PostgreSQL.
- **Очередь:** Redis + RQ; отдельный worker, статусы в PostgreSQL.
- **AI:** faster-whisper + FFmpeg; локальный Ollama/Qwen по результатам замеров; резервная оценка по правилам.
- **Frontend:** React, TypeScript, Vite, Tailwind CSS, Recharts.
- **Инфраструктура:** Docker Compose для PostgreSQL/Redis и сервисов, конфигурация через `.env` (пример без секретов).
- **Тесты:** pytest, httpx, Playwright; линтеры Ruff и ESLint.

**Оборудование разработки:** MSI Modern 14, Intel Core i5-1235U, Intel Iris Xe, 16 ГБ RAM. CUDA недоступна. Модели должны работать на CPU или на выделенном сервере; GPU-ускорение на ноутбуке не предполагается.

## 6. Архитектура и потоки данных

```text
Browser (React)
    |
    v
FastAPI -- PostgreSQL (пользователи, звонки, транскрипты, KPI, аудит)
    |  \
    |   \-- protected local storage (audio, exports)
    v
Redis/RQ --> AI Worker --> FFmpeg --> faster-whisper
                       |                  |
                       +--> KPI rules / local Ollama
                       |
                       +--> PostgreSQL (результаты, статусы)
```

Аудио хранится вне общедоступной статической директории. Выдача файлов идёт через API после проверки прав. Redis не считается единственным источником истины о статусах.

## 8. Модель данных (основные таблицы)

- `users`: id, username, password_hash, role, active, created_at.
- `operators`: id, user_id (nullable), name, team_id.
- `calls`: id, operator_id, uploaded_by, started_at, duration_sec, format, storage_key, status, error_message, created_at.
- `transcript_segments`: id, call_id, start_sec, end_sec, speaker, text, confidence (nullable).
- `evaluation_profiles`: id, name, version, weights_json, rules_json, active.
- `evaluations`: id, call_id, profile_id, model_version, total_score, summary, created_at, reviewed_by (nullable).
- `criterion_scores`: id, evaluation_id, criterion, score, evidence_json.
- `violations`: id, evaluation_id, criterion, severity, start_sec (nullable), end_sec (nullable), explanation, recommendation.
- `audit_events`: id, actor_id, action, resource_type, resource_id, timestamp, metadata_json.

Использовать миграции Alembic, внешние ключи, индексы по датам/операторам/статусам и уникальные ограничения там, где нужно.

**Готово, когда:** API работает с реальной БД; запрещён доступ к чужим данным; Swagger соответствует контрактам; миграции применяются на чистой БД.

### Участник 2 — AI Lead / Speech-to-Text / NLP
**Зона владения:** `backend/app/services/transcription.py`, `evaluation.py`, `audio.py`.

Задачи:
1. Подключить FFmpeg и faster-whisper CPU int8.
2. Обеспечить распознавание WAV/MP3/OGG, сегменты с таймкодами.
3. Подготовить базовый движок KPI с объяснениями и статусом «неизвестно».
4. Подключить Ollama/Qwen как опциональный локальный анализатор с JSON-валидацией и таймаутами.
5. Отдельно оценить качество распознавания и время обработки 1/5/10 минут.
6. Подготовить безопасную стратегию speaker labels; не обещать точную диаризацию без проверки.

**Готово, когда:** функция `process_audio(path)` выдаёт валидные сегменты; `evaluate(transcript, profile)` выдаёт структурированный результат; тесты работают без внешних сервисов.

**Готово, когда:** пользователь может пройти весь сценарий без Swagger; UI корректно отображает загрузку, ошибки и завершённые задания.

**Готово, когда:** несколько файлов становятся в очередь, worker их обрабатывает, ошибки не теряются, после перезапуска сервисы поднимаются без потери сохранённых данных.

## 12. Приоритеты при нехватке времени

**P0 (обязательно):** offline, загрузка форматов, очередь, распознавание, транскрипт с таймкодами, объяснимая оценка, базовый дашборд, CSV/JSON, обработка ошибок, тест полного цикла.

**P1 (желательно):** роли и защищённая выдача аудио, массовая загрузка, настройка KPI, графики динамики, повторная обработка, аудит, ручная проверка оценок.

**P2 (после MVP):** продвинутая диаризация, интеграции телефонии, корпоративный SSO/MFA, PDF, расширенная семантическая аналитика, кластеризация тем, высокодоступная инфраструктура.

**Правило:** не жертвовать работоспособностью P0 ради эффектных P2-функций.

## 13. Критерии приёмки MVP

- [ ] Запуск локально по README без обращения к внешним AI API.
- [ ] WAV, MP3, OGG корректно принимаются и расшифровываются.
- [ ] При загрузке 5 файлов отображается очередь; обработка не блокирует интерфейс.
- [ ] Есть реальные сегменты расшифровки с таймкодами.
- [ ] Оценка содержит критерии, итоговый балл, объяснения и рекомендации.
- [ ] Сомнительные выводы помечены, а не выданы за факт.
- [ ] Дашборд использует реальные сохранённые данные.
- [ ] CSV/JSON содержит требуемые поля и корректные значения/null.
- [ ] Доступ к звонкам и аудио проверяется на сервере.
- [ ] После перезапуска данные сохранены; ошибки задач видны.
- [ ] Измерена обработка 10-минутной записи на целевом оборудовании; зафиксирован результат относительно 3–5 минут.
- [ ] Проведён тест с отключённым интернетом после предварительной установки моделей.

## 14. Отдельные условия для банковского пилота

## 15. Правила совместной разработки

1. Git: ветки `feature/<module>`, PR с ревью; `main` всегда запускается.
2. Изменения схем БД только через Alembic; API-контракты согласовываются до интеграции.
3. Каждая задача: код + тест + инструкция проверки; никаких паролей и реальных клиентских данных в Git.
4. Ежедневная интеграция; короткий стендап утром и демонстрация вечером.
5. AI-модули должны иметь интерфейсы и тестовые заглушки, чтобы frontend/backend не блокировались загрузкой моделей.
6. Нельзя подменять работающую обработку заранее записанными результатами без явной маркировки «демо».
